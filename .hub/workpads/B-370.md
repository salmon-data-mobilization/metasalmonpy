### Why the loop's copy is the narrowest place

The `attrs` travel from `find_terms()`, through `_search_once_per_call()`,
into the loop's copy, and from there to `pd.concat`. Each place on that path
was weighed:

1. **`find_terms()`**, where the `attrs` are set. Removing them changes what
   every caller reads, which the condition forbids and which would be class 2.
2. **`_search_once_per_call()`**, B-243's wrapper. It reads the diagnostics to
   decide what to keep, and its answers are meant to be `search_fn`'s. Handing
   back copies without `attrs` would make them differ, and it would not cover
   the loop run without the wrapper. Measured below: that wrong fix fails
   B-243's per-target reference, which runs the loop without the wrapper.
3. **The loop's copy**, chosen. It is the first point at which the frame
   belongs to the loop and to nothing else: before it, `res` is the answer a
   search returned, which `find_terms()`'s caller, an injected `search_fn` or
   the wrapper's kept copy may still hold. Every frame the loop appends
   descends from this copy, so one line covers all of them, and nobody else's
   object is touched. Measured below: dropping the `attrs` from the answer
   itself, before the copy, fails the new test's last assertion.
4. **At `pd.concat`.** The same frames, so no narrower in what it changes, and
   later: each frame would carry the diagnostics through the loop's filter,
   sort and `head()`, and pandas 2.1 and later deep-copies `attrs` at each of
   them.

The drop is not a workaround for pandas. A search's diagnostics describe that
one search, and a candidate table built from several answers has none of its
own. So nothing retires it.
