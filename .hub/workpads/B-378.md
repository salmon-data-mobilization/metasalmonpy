### Why a sink, and why the detail comes off the prefix

R's `.safe_json()` signals a `metasalmon_search_failure` condition that nobody
handled in the ICES helpers, and B-377's `.ices_request()` handles it. The
Python counterpart of that condition is `_signal_search_failure()`, which
records into the innermost sink on `_search_failure_sinks`, and only when one
is installed. `find_terms()` installs one per source call. So the port
installs one per ICES request, which is the shape the hub's port note
anticipated (*"`ices_vocab.py` installs none"*).

R's warning names `failure$detail`, the bare failure (`HTTP 503`). A Python
sink records `Vocabulary API request failed: HTTP 503`, the text
`find_terms()` joins into its diagnostics. Three ways to get the detail were
weighed. Making the record carry `detail` (a `str` subclass) keeps
`find_terms()` unchanged but needs its own pickling support. Changing the
record to a tuple breaks `find_terms()`'s join and the diagnostics tests that
compare records with strings. Naming the prefix once and taking it off with
`str.removeprefix()` (Python 3.9, the declared minimum) changes one line of
`term_search.py` and nothing any caller reads. The third was chosen.

## Found, not absorbed

Neither has a queue item. Searched `queue/items/` at metasalmon `14f6d4f` for
`curl`, `safe_json`, `fallback`, `empty body`, `thread` and the sink's name,
with `ices_code_types` as the positive control (it returned B-377 and B-378);
the hits were about other fallbacks.

1. **Candidate: `_safe_json()` asks a failed request again through curl, and
   reads curl's empty output as no answer.** metasalmon's `.safe_json()` makes
   one `httr::GET()` and has no fallback. With curl on `PATH`, as it is on
   this machine, a connection failure, a timeout and an unparseable answer are
   each requested twice, and an HTTP 200 with an empty body gives `None` with
   no recorded failure. So the ICES helpers give no warning for it (measured
   above), and, by reading `_safe_json()` and `find_terms()`, the search
   records `status="success"`, where metasalmon records a failure and warns.
   Neither register records the fallback: `PARITY.md` and metasalmon's
   `parity-deviations.md` mention curl only for the licence-URL normaliser
   (row 26). The fallback was written for broken local HTTPS stacks (the
   comment in `_safe_json()`), so whether it should stay, and if so whether an
   empty body should count as a failure, is the question. The repo would be
   metasalmonpy.
2. **Candidate: the failure sinks are one list for the process.**
   `term_search._search_failure_sinks` has no lock and is not per thread. A
   caller running `find_terms()` on several threads can have one call's
   failure recorded in another call's sink, and a pop can remove another
   call's sink, so a source can read `status="success"` while its request
   failed, and a degraded lookup can be cached, which the cache rule exists to
   prevent. Read, not measured. This branch guards its own use (*Guards
   added*) and leaves `find_terms()` as it was.

## Guards added, and what retires them

- `_ices_request()` warns only when `_safe_json()` answered `None`
  (`if data is not None or not failures: return data`). `_safe_json()` answers
  `None` whenever it records a failure, so in one thread this is exactly R's
  `if (is.null(failure)) return(data)`. It routes around candidate 2: a failure
  from a call on another thread can land in this call's sink, and without the
  condition it would replace an answer this call received with an empty frame
  and a warning. **Retires when** the sinks are per thread, so a failure can
  only reach the sink of the call that made it. The comment at the condition
  says so.
