### Why a sink, and why the detail comes off the prefix

R's `.safe_json()` signals a `metasalmon_search_failure` condition that nobody
handled in the ICES helpers, and B-377's `.ices_request()` handles it. The
Python counterpart of that condition is `_signal_search_failure()`, which
records into the innermost sink on `_search_failure_sinks`, and only when one
is installed. `find_terms()` installs one per source call. So the port
installs one per ICES request, which is the shape the hub's port note
anticipated (*"`ices_vocab.py` installs none"*).

R's warning names `failure$detail`, the bare failure (`HTTP 503`). A Python
sink records `Vocabulary API request failed: HTTP 503`, the text
`find_terms()` joins into its diagnostics. Three ways to get the detail were
weighed. Making the record carry `detail` (a `str` subclass) keeps
`find_terms()` unchanged but needs its own pickling support. Changing the
record to a tuple breaks `find_terms()`'s join and the diagnostics tests that
compare records with strings. Naming the prefix once and taking it off with
`str.removeprefix()` (Python 3.9, the declared minimum) changes one line of
`term_search.py` and nothing any caller reads. The third was chosen.

### Why the sinks are per thread

The first push, `9c600c0`, installed the ICES sink on the stack `find_terms()`
already used, one list for the process. Knowing that list was shared, it
guarded the helper: it warned only when its own request answered `None`, so
that a failure recorded by another thread could not replace an answer. The
Codex review of `9c600c0` found the stack itself wrong (review thread on
`ices_vocab.py` lines 37 to 41): on two threads, one call's `pop()` could
remove the other's sink, and a failure landed in whichever sink was installed
last. So a failed request could still lose its warning, which the guard did
not prevent, and an ICES request on one thread could now corrupt a concurrent
`find_terms()` call's diagnostics, which widened a hazard this workpad had
recorded only as a candidate. The finding was right, and `219fc6b` reproduces
it before `e336023` fixes it.

An R calling handler is installed around one call stack and hears only the
failures inside it. A Python thread is the closest thing to that call stack
here: `find_terms()` and the ICES helper push, call `_safe_json()` and pop on
the thread they run on, and nothing in the package runs them on a thread of
its own. So the stack is per thread (`threading.local`), and it keeps the list
operations its callers use, which is why no caller and no existing test
changed. The guard went with the cause: it said it retires when the sinks are
per thread, and `e336023` made them so, which returns the helper to R's shape,
`if (is.null(failure)) return(data)`.
