**All four cells differed, and they differed in four ways at once** —

### The mechanism, probed rather than assumed

```
dtypes:              {'temporal_start': 'datetime64[us]', 'temporal_end': 'datetime64[us]'}
to_csv:              'temporal_start,temporal_end\n999-06-05 13:45:30,2024-12-31\n'
object-dtype to_csv: 'temporal_start,temporal_end\n0999-06-05 13:45:30,2024-12-31 00:00:00\n'
str(S)               '0999-06-05 13:45:30'
S.isoformat()        '0999-06-05T13:45:30'
to_csv, all midnight 'e\n2024-12-31\n'
to_csv, mixed        'e\n2024-12-31 00:00:00\n2024-12-31 01:00:00\n'
```

A column built from `datetime.datetime` becomes `datetime64[us]`, and `to_csv`
renders it through pandas' **column-wise** formatter: unpadded year below 1000,
space separator, and the time dropped entirely when every value in the column
is midnight. `str()` of the same value and an object-dtype column both pad and
keep the time. So `resource_types.py`'s header claim — that the padded form is
what the module converges on — was true of every path it rendered itself and
false of the one pandas rendered for it, exactly as the item said.

**The last two lines are the part worth keeping.** One cell's bytes depend on
the other rows in its column. That is `.ms_sssom_canonical_bytes()`'s defect in
pandas, and it is what `AGENTS.md`'s *one value, one rendering* contract is
about rather than a spelling difference.

## What I changed and where

**The baseline this renderer sits on, named before changing anything**, because
`AGENTS.md` says the baseline decides and not the type.

R's fix moved the *descriptor* onto the CSV's baseline, because
`readr::write_csv()` already emits the ruled form and could not move. **Here
neither of those holds.** `to_csv` cannot emit `Z` for a naive `datetime64`
column at all, so the CSV's baseline cannot be the ruled spelling; and this
package already has that spelling, in `resource_types._iso_seconds(...) + "Z"`,
which is what `render_resource_frame()` writes into every data resource. So
**both** metadata outputs move onto the package's own instant renderer, and
data resources, metadata CSVs and the descriptor end up spelling an instant
identically — which is stronger than what was asked and is the form the
contract asks for.

1. **`resource_types.py` — `iso_instant_text()`**, the one rendering of an
   instant as bytes this package writes, with the three load-bearing details
   stated on it: UTC folding, padding by construction rather than through
   `strftime`, and truncation of the fractional second.

   **It replaced four inline copies, and the copies did not agree.** The string
   `_iso_seconds(x) + "Z"` stood at four call sites across two modules:
   `render_resource_frame()` twice, `observation_structures._typed_character()`
   and `._normalize_typed_values()`. **Two of them wrote a different string
   from the other two for the same tz-aware instant**, measured on the pre-fix
   tree rather than reasoned about:

   ```
   datetime(2024, 12, 31, 0, 0, 0, tzinfo=UTC-08:00)
   render_resource_frame, object dtype : 2024-12-31T00:00:00Z   <- local clock wearing a Z
   render_resource_frame, datetime64tz : 2024-12-31T00:00:00Z   <- same
   _typed_character                    : 2024-12-31T08:00:00Z   <- correct
   readr::write_csv() (R 4.3.3/readr 2.2.0) : 2024-12-31T08:00:00Z
   ```

   Only `_typed_character()` folded to UTC; `._normalize_typed_values()` was
   handed a value `_parse_datetime()` had already folded; neither branch of
   `render_resource_frame()` folded at all. **Every suite stayed green**,
   because each test built its expectation with the same call it was testing.
   That is the "found by reading, not by a guard" failure `AGENTS.md`
   describes, and it is why this is one function rather than an agreement

   **This is a second convergence onto metasalmon, and it is deliberate rather
   than scope creep.** readr folds to UTC, so `render_resource_frame()` was
   diverging from R for a tz-aware column and nothing recorded it. After the

### Why one assertion is a literal where the brief preferred a shape

The brief asked for agreement plus a shape regex over a hard-coded literal
year, which is what B-115 did. **Both are here, and there is also a literal,
deliberately — this is the one place I depart from the brief, and the reason is
a measurement.**

B-115 used a shape because R's year is **platform-dependent**: readr writes
`999-…` on Linux and `0999-…` on macOS, so a literal would fail on one of the
two. Here the year is padded **by construction** — `resource_types._iso_date`
builds it with `%04d` and never reaches `strftime`, which is the property this
whole guard file exists to keep — so a literal costs nothing in portability and
buys the one thing a shape cannot: if this path is ever routed back through
`to_csv` or `strftime`, the padding goes and only the literal notices.

So the tests are layered on purpose:

* `test_datapackage_json_and_dataset_csv_spell_an_instant_identically` asserts
  **agreement** and nothing else. It is B-145's actual obligation, it survives
  any later ruling on the spelling, and whichever writer moves next the two
  still have to move together.
* `test_a_written_instant_takes_the_ruled_iso_form` asserts the **shape**
  (`^[0-9]+-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$`), so a B-161 ruling
  can change the year digits without rewriting it.
* `test_a_written_pre_1000_instant_keeps_its_padded_year` asserts the
  **literal**, and its docstring says in as many words that it pins what this
  implementation does and rules nothing about what it should do.

Supporting measurements on this container, each run directly:

```
readr::format_csv(data.frame(v = as.POSIXct("0999-06-05 13:45:30", tz="UTC")))  ->  999-06-05T13:45:30Z
readr::format_csv(data.frame(v = as.POSIXct("2024-12-31 00:00:00", tz="UTC")))  ->  2024-12-31T00:00:00Z

```

**So, stated as a measurement:**

* Each implementation now agrees **with itself**, on both platforms. That is
  what B-115 and B-145 between them achieve, and it holds regardless of the
  year.
* For an instant at or after year 1000 — `2024-12-31T00:00:00Z` — the two
  implementations agree **exactly**, byte for byte, in both files.
* Below year 1000 they differ **on Linux, by exactly one leading zero**:
  `0999-…` here, `999-…` there. On macOS they would agree, per the cited row.
* The two are padded differently for reasons neither of which is arbitrary. R
  follows `readr::write_csv()`, whose `%Y` is its build's libc. This package
  pads by construction, which `PARITY.md` row 40 already registers and
  `tests/test_platform_determinism_guard.py` exists to keep true — so matching
  R's Linux output would mean deliberately undoing that guard, which is a
  ruling and not an implementation detail.

**Which year is correct is hub item B-161** (`repo: metasalmon`, `claimable:
false`, Brett's). I did not touch it, and I did not pick a year-padding
behaviour and call the item done: what is here is what this package already
does, measured against what R already does.

One thing worth saying because it is not obvious from B-161's text: **this
branch does not widen that gap and does not narrow it either.** Before the fix
the Python descriptor was already padded (`0999-…`, from `isoformat()`), and
the Python CSV was already unpadded (`999-…`, from `to_csv`) — so before, the
two implementations disagreed in *both* directions at once depending on which
file you read. After, Python is consistently padded and R consistently follows
readr, which is a smaller and legible difference. That is a consequence of
making each side self-consistent, not a decision about the year.

## A correction made inside this item, recorded rather than quietly fixed

The first commit on this branch (`34c226e`) says in its message, and the pull
request body said, that `_iso_seconds(x) + "Z"` stood at **five** call sites and
that *"two of them folded a tz-aware value to UTC first and three did not"*.
**That count was wrong and the split was wrong.** There were **four** pre-existing
call sites, and the true split is: one folded (`_typed_character`), one received
an already-folded value (`_normalize_typed_values`), and two did not fold at all
(`render_resource_frame`, both branches).

It is recorded here rather than silently corrected because it is the failure
`AGENTS.md` names — a claim stronger than its measurement — committed inside the
pull request whose subject is that failure. The commit message cannot be amended
(no force-push), so the correction lands as a second commit and this paragraph is
the pointer between them.

**The pull request body still carries the wrong count, and it is left that way
on purpose.** Editing a pull request body is not among the five pull-request
operations `HUB.md`'s writes register permits, and the register is closed — an
operation resembling a permitted one is denied unless it is named. So the body's
*"stood at five call sites … two of them folded … and three did not"* sentence
is **stale and known to be**, and this file plus commit `fc9e0ff` are the
correct record. Affects no check. The fix for it was to **measure** rather than to
recount: the pre-fix and post-fix tz behaviour of every call site is now in the
