Where the test departs from the R test, and why:

1. **Two tags.** `!expr` is the twin. No Python loader evaluates it unless
   taught to, so on its own it catches a PyYAML swap only as an unknown-tag
   error (M1 below). `!!python/object/apply:os.mkdir` is the tag PyYAML's
   permissive loaders do execute, so the same swap trips the side effect.
2. **The `!expr` expression is Python**, `open(<sentinel>, "x").close()`, where
   R's is `file.create(<sentinel>)`, so a loader taught to evaluate the tag
   would create the sentinel rather than raise a `NameError`.
3. **A positive control.** A spy on `sssom.read_sssom_mapping_set` records what
   the validator read, and the test asserts the tagged file is among it.
   Without it, a validator that stopped reaching the reader would pass this
   test, with nothing evaluated, for the wrong reason.
4. **No option to turn on.** R sets `yaml.eval.expr = TRUE` to model the worst
   session. The subset parser reads no global state, so there is nothing here
   to set.
5. **The text as written, tag included.** R returns the text without the tag;
   see *Not this item*.

- **Candidate, no id yet: the two SSSOM readers return different text for a
  tagged scalar.** For `mapping_set_title: !expr X`, metasalmon's
  `read_sssom_mapping_set()` returns `X`, because yaml drops the tag, and
  metasalmonpy's returns `!expr X`. Measured above on one file. Neither register
  mentions tags. It is the SSSOM-header counterpart of Q-62, which asks the same
  question for the EML sidecar's reads only, and a ruling on which side moves is
  Brett's. The test here pins today's Python text, so a ruling that moves Python
  changes one assertion in it.

  rationale. The test's docstring says only that `yaml::yaml.load()` can
  evaluate `!expr`, so it repeats none of it.
