## What this is, and which direction it runs

Brett ruled the three-column migration-report shape on **2026-09-14, for both
implementations**. The R half landed as metasalmon pull request **#117** (hub
**B-112**, backlog #112). This is the mirror half, and it runs **backwards**:

## The test, and why it pins three branches rather than one

The item asks for a test pinning the column set of **both** branches. This pins
**three**, matching R's counterpart exit for exit: the nothing-to-migrate early
return, the populated build, and the no-placement empty frame. Pinning only the
branch that was wrong leaves the other two free to drift away from it, and that
failure would look identical from the outside. It asserts column **order** as
well as membership (mirroring R's `expect_named()`), the `object` dtype at all
three, and the row counts 0/1/0 — that last so the column set cannot be
satisfied by an exit that gained the column by gaining a row it should not have.

*Retires when:* `migrate_sdp_methods()` stops returning a `tables` frame, at
which point there is no shared column set left to pin. (Stated in the test's own
header, as every guard here must.)

## The register decision: amended in place, no new number

**Row 9 amended in place. No number minted. Row count unchanged at 61.**

Three reasons, in the order they matter.

1. **Row 9 already owns this divergence.** It is the registry/migration row, and
   the sentence that went stale is its own: *"The migration itself is mirrored
   1:1 against metasalmon `main` (`e02111a`)"*. A new row would leave that
   claim standing while a second row contradicted it, and this file names a row
   that still reads as a passing verification as the worst shape a stale row can
   take. The R half reached the same conclusion for the same row on the hub
   side (`ef0d764`).
2. **A port is not a deviation.** Catch-up to a ruling is not a chosen
   difference, and the hub register says filing absence as design is the one
   thing these registers must not do.
3. **`check-parity-registers.py` goes red on a number present in one register
   and absent from the other.** Minting a number here alone would turn both
   repositories' guards red, and the twin edit cannot ride this pull request —
   see the residual below. Amending in place keeps the number sets identical,
   which the three runs above confirm.

The convention this follows is already written in `PARITY.md`: *"Rows 9, 27, 33,
38 and 46 were updated at S10 chunk A … No new number was spent; the hub
register carries the same five updates."*
