## What readr reads, measured before any Python was written

R 4.3.3, readr 2.2.0, `TZ` `Etc/UTC`, C locale. `readr::parse_datetime()`, one
token at a time and on the whole vector, and `readr::read_csv(I(...))` with a
`col_datetime()` column agree on every value, and `problems()` is empty for
each:

| token | `print()` | `format()` | epoch second | `readr::write_csv()` writes |
|---|---|---|---|---|
| `0001-01-01T00:00:00+01` | `"0-12-31 23:00:00 UTC"` | `0-12-31 23:00:00` | -62135600400 | `0-12-31T23:00:00Z` |
| `0001-01-01T00:30:00+01` | `"0-12-31 23:30:00 UTC"` | `0-12-31 23:30:00` | -62135598600 | `0-12-31T23:30:00Z` |
| `9999-12-31T23:00:00-02` | `"10000-01-01 01:00:00 UTC"` | `10000-01-01 01:00:00` | 253402304400 | `10000-01-01T01:00:00Z` |

The tibble prints the column as `<dttm>`: `0-12-31 23:00:00`,
`0-12-31 23:30:00`, `10000-01-01 01:00:00`. `as.POSIXlt()` gives year 0 and
year 10000. One second inside each end, `0001-01-01T01:00:00+01` reads as
`"1-01-01 UTC"` (-62135596800) and `9999-12-31T21:59:59-02` as
`"9999-12-31 23:59:59 UTC"` (253402300799). One second outside,
`0001-01-01T00:59:59+01` reads as `"0-12-31 23:59:59 UTC"` and
`9999-12-31T22:00:00-02` as `"10000-01-01 UTC"`.

metasalmon `main` `9aeb0ec`, loaded with `pkgload::load_all()`:

- `.ms_convert_declared_tokens()` returns the three as POSIXct, reason `NULL`.
- `read_salmon_datapackage()` reads the r-package with `survey_time[1]` set to
  each, at the epoch seconds above, with no mismatch attribute, and
  `validate_salmon_datapackage()` returns.
- `.ms_canonical_value_tokens()` keys them `0000-12-31T23:00:00.000000Z`,
  `0000-12-31T23:30:00.000000Z` and `10000-01-01T01:00:00.000000Z`, from the
  text and from the POSIXct alike, and the four boundary tokens
  `0000-12-31T23:59:59.000000Z`, `0001-01-01T00:00:00.000000Z`,
  `9999-12-31T23:59:59.000000Z` and `10000-01-01T00:00:00.000000Z`.
- With `survey_time` coded in `codes.csv`, the package validates with no issue.
  With the token's row removed, validation fails naming the key: *Table 'obs'
  column 'survey_time' has data values not listed in codes.csv:
  0000-12-31T23:00:00.000000Z.*

So readr reads every token, and metasalmonpy can hold the same instant:
`numpy.datetime64` at microsecond resolution, under pandas 3.0.6, 2.2.3 and
1.5.3. `pd.Timestamp` cannot be that type everywhere: under pandas 1.5.3,
`pd.Timestamp(np.datetime64(-62135600400000000, "us"))` raises
`OutOfBoundsDatetime`.

## What changed, and where

- `resource_types.py`:
  - `parse_datetime_token()`: when applying the offset overflows, it returns
    `np.datetime64(value, "us") - np.timedelta64(shift)`. A token whose instant
    a `datetime` holds returns exactly what it did.
  - `_epoch_seconds()` takes a `numpy.datetime64` too: integer microseconds over
    10**6, the division `timedelta.total_seconds()` makes.
  - `format_datetime_token()` renders through `_utc_fields()` (new), which reads
    the calendar fields of any epoch second after moving it into the 400-year
    Gregorian cycle that starts at the epoch. Checked outside the suite against
    `_EPOCH + timedelta(seconds=...)` on 200,009 seconds in years 1 to 9999, and
    against `str(np.datetime64(s, "s"))` on 40,006 seconds outside them: no
    difference.
  - `canonical_value_tokens()`: a `Timestamp` outside years 1 to 9999 (pandas
    3's column holds them) goes through `_timestamp_instant()` (new) to its
    `numpy.datetime64`, because `to_pydatetime()` raises `ValueError` for it. A
    `numpy.datetime64` that is not NaT is keyed directly. A NaT goes the way it
    went before.
  - `typed_series()`: comment only. Its fallback already holds these values.
  - `import numpy as np`, which every supported pandas requires.
- `metadata.py`: docstring only, in `_readr_reads_as_date_time()`
  (*Not done*).
- `tests/test_instant_beyond_datetime_range.py` (new, 20 tests).
- `CHANGELOG.md`: one entry under `## Unreleased`, `### Fixed`.
- `AGENTS.md`: the dated suite counts.

## Not done, and why

- **Writing such a value back out.** Not in the retirement condition. Under
  pandas 3.0.6, `write_salmon_datapackage()` raises `ValueError: year 0 is out
  of range` (and `year 10000`) from `iso_instant_text()`. Under 2.2.3 and 1.5.3
  it writes `0000-12-31T23:00:00.000000`, which this package reads back as a
  type mismatch. metasalmon's own round trip fails too: it writes
  `0-12-31T23:00:00Z` and `10000-01-01T01:00:00Z`, and its reader reports both
  as *unparseable as that type* (metasalmon `9aeb0ec`, R 4.3.3). Choosing a
  spelling for year 0 and year 10000 is a spelling ruling, next to B-161's for
  the years before 1000 (*Found*, item 1).
- **Validating an observation structure that binds such a column.** The same
  renderer. Measured on the fixture of `test_a_datetime_dimension_is_accepted`
  with `observed_at[1]` set to each token: pandas 3.0.6 raises `ValueError:
  year 0 is out of range`; 2.2.3 and 1.5.3 raise *Observation component values
  do not match their dictionary value_type*. metasalmon returns for
  `0001-01-01T00:00:00+01` and raises that message for
  `9999-12-31T23:00:00-02` (*Found*, item 1).
- **The `except OverflowError` in `metadata._readr_reads_as_date_time()`.**
  B-188 added it for this overflow, and nothing reaches it now, because the
  parser returns for those tokens; the tests B-188 pinned them with in
  `tests/test_codes_target_categorical.py` still pass. A workaround is a guard
  in `AGENTS.md`'s sense, and deleting one is `HUB.md` class 6, so this branch
  leaves it and corrects the docstring, which said the parser returns only a
  `datetime` (*Found*, item 2).
- No metasalmon half and no `PARITY.md` row: readr already reads these tokens.

## Found, not absorbed

1. **Candidate, metasalmonpy and metasalmon: an instant before year 1 or after
   year 9999 does not survive a write in either package.** Measurements under
   *Not done*. In metasalmonpy it is `iso_instant_text()`, which also serves
   the observation-structure validator. In metasalmon, `readr::write_csv()`
   writes a year its own reader refuses. A fix needs the spelling ruled first,
   so this is probably a question for Brett beside B-161 before it is two
   items.
2. **Candidate, metasalmonpy: retire the dead `except OverflowError` in
   `metadata._readr_reads_as_date_time()`.** Its cause is gone once this branch
   merges. Deleting it is class 6, so it is Brett's to approve.
3. **Candidate, metasalmonpy: a year-0000 token.** readr reads
   `0000-06-01T00:00:00Z` and `0000-12-31T23:00:00Z` as POSIXct (epoch
   -62154086400 and -62135600400), `parse_date("0000-06-01")` as a `Date`, and
   `0000-12-31T23:00:00.000000` too. metasalmonpy reports every one of them as
   *unparseable as that type*, for `datetime` and for `date`, because
   `datetime(0, ...)` raises and the parser returns `None`. So a package R reads
   fails here. Measured on `main` `c7be120` and on this branch, with the same
   result: such a token never reaches the offset.
4. **Candidate, metasalmonpy: a blank value in a coded `datetime` column.**
   `validate_salmon_datapackage()` raises `ValueError: cannot convert float NaN
   to integer` on the r-package with `survey_time[1]` blank and the other three
   listed in `codes.csv`, on `main` `6f1a191` under pandas 3.0.6 and 1.5.3.
   `canonical_value_tokens()` takes the `pd.NaT` a typed column holds for
   `datetime`, because `NaTType` subclasses `datetime`, and
   `format_datetime_token()` floors NaN. metasalmon returns with no issue on the
   same package. This branch leaves that path as it was, and measured on it the
   error is unchanged.
5. pandas 1.5.3, the declared minimum, fails tests on `main` and on this branch
   alike, none in this path. That is B-274's candidate 6, already named in its
   workpad.
